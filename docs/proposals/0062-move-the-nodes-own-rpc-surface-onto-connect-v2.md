# Move the node's own RPC surface onto connect v2

This proposal moves the RPC services the node authors — the node directory,
the link service, the voting application's submission, the WireGuard
application's directory — from connect-go v1 to
[v2](https://github.com/connectrpc/connect-go/blob/main/docs/v2-migration.md),
and holds the drafts' control plane on v1, where scionproto's generated code
anchors it. No `.proto` file changes, no service path moves, and no wire
message is re-encoded: a v2-built node answers a v1-built peer byte for
byte. What changes is the Go surface the four services and their four
clients are written against.

## Summary

The repository's connect surface splits in two. The larger half implements
the SCION Internet-draft services — beaconing, segment registration and
lookup, trust material, chain renewal — against
`control_planeconnect`, the package scionproto/scion generates with v1 and
[buf.gen.yaml](/buf.gen.yaml) only mirrors; it cannot move until upstream
does. The smaller half is the node's own: four services, six unary RPCs,
generated from the four protos in
[/proto](/proto) into `nodev1connect`, `votingv1connect`, and
`wireguardv1connect`. That half is this proposal's scope.

The used feature surface is narrow: unary handlers and clients, the
`connect.Request`/`connect.Response` wrappers, `connect.NewError` with the
`Code*` constants, and `connect.CodeOf` in one client. No interceptors, no
streaming, no headers or trailers read, no codec or compression options, no
error details — identity rides `peeria`'s plain `http.Handler` middleware
and the address rides `http3`'s context, both indifferent to the connect
version beneath them. Every v2 change that touches this repository is
therefore one of four shapes: the module path, the generated code, the
wrappers leaving, and the error constructor taking a message.

## Motivation

v1 remains supported — fixes and security updates — but v2 is where
connect-go develops. The node's own services are where new RPCs get added:
every application seam so far has grown one. Writing the next against v1
after v2 exists accrues
code the migration guide already documents the retirement of, while the
eventual move is forced anyway: the drafts' control plane anchors v1 in
`go.mod` until scionproto migrates, so a split pass now and a scion-triggered
pass later is the same total work as one late pass, with the node's own
surface off the critical path.

Two v2 defaults also land where this repository already stands. v2's
`connect.NewError` takes a message, not an error, so the plain `err` a
handler forwards today — the trust engine's own words, on the wire to a peer
— becomes a message the node states, with the cause chained server-side via
`WithCause`. And v2 bounds message reads at 4 MiB where v1 read without
limit: validation at the boundary, of the kind the coding style asks for,
arriving as a default instead of a decision.

### Goals

*   The four own services and their four clients compile against
    `connectrpc.com/connect/v2`: handlers take and return the protobuf
    messages themselves, clients call them with the message and read the
    reply directly.
*   The generated `*connect` packages are regenerated by a v2
    `protoc-gen-connect-go`, and [buf.gen.yaml](/buf.gen.yaml)'s pinned
    versions say so.
*   Error sites state their own wire-visible message and chain their cause
    with `WithCause`; `CodeOf` keeps mapping the voting submitter's absence
    answer.
*   The 4 MiB read bound is adopted as it ships — no `WithReadMaxBytes(0)`
    pin preserving the v1 non-behavior.
*   `go.mod` carries both modules for the interim: `connect` v1 beside
    `connect/v2`, the first serving the drafts' control plane alone.

### Non-goals

*   No migration of the drafts' control plane —
    [server.go](/pkg/core/controlplane/server.go),
    the service implementations, `NewClient`, `PeerClient`, and the WebPKI
    remote all stay on v1 with the scionproto package they serve; a
    follow-up proposal moves them when upstream generates v2 code.
*   No feature adoption beyond the move: no interceptors, no
    `connectinprocess` test transport, no codecs, compression, health, or
    reflection services — the in-memory `RoundTripper` the voting test uses
    and the full-stack labs already cover those seams.
*   No native transport beneath the channel — v2's core no longer depends
    on `net/http`, which makes a QUIC-stream transport conceivable, but it
    would reframe the protocol every peer speaks; the channel stays HTTP/3
    over SCION as the control plane draft and
    [ADR-0020](/docs/adrs/0020-file-the-scion-native-channel-as-a-library.md)
    fixed it.
*   No `.proto` edits, no path or protocol changes, no read-limit tuning
    beyond accepting the default.
*   No ADR — no boundary moves; the seams keep their shape and exchange one
    library for its successor.

## Proposal

### The two connects in one module

v2 lives at `connectrpc.com/connect/v2`, so both versions import side by
side: the control-plane packages keep `connectrpc.com/connect`, everything
the node owns takes the `/v2` path. The two never meet in a type — the
drafts' handlers, `NewClient`'s exported `connect.HTTPClient` and
`connect.ClientOption` signature, and the WebPKI remote stay v1; the four
own seams go v2 wholesale, package by package, with no call crossing
between the sets. The guide builds for exactly this interim. The libraries
both sets ride — `peeria` and `scionrpc` — name no connect symbol and do
not move: v2 keeps the seam they live on, `connecthttp` still consuming an
`*http.Client` and a base URL and still yielding an `http.Handler`, so the
hex-encoded peer authority that carries a SCION address through the URL to
the dialer stays exactly as
[ADR-0020](/docs/adrs/0020-file-the-scion-native-channel-as-a-library.md)
filed it.

### The generated code

The four `*connect` packages are regenerated, not edited. The v2
`protoc-gen-connect-go` installs from the v2 module,
[buf.gen.yaml](/buf.gen.yaml)'s version pins are restated for it, and
`buf generate` rewrites the four generated files in place — the
`IsAtLeastVersion1_13_0` assertions leave
with the regen. The config carries no style option and v2's simple style is
the only style, so nothing is rejected and nothing is added. The
constructor change lands in the same files: the generated handler
constructor no longer returns an `(http.Handler, string)` pair but
registers on a `*connect.Server`, and the client constructor takes the
`connect.NewClient`-wrapped transport.

### The services

Each own service implements the regenerated interface: the method takes
the request message and returns the reply message, so
`connect.NewResponse(...)` leaves every handler —
[voting.go](/pkg/apps/voting/voting.go),
[directoryservice.go](/pkg/apps/wireguard/directoryservice.go),
[directory.go](/pkg/modules/topology/impl/measured/directory.go), and
[linkservice.go](/pkg/modules/topology/impl/measured/linkservice.go) — and
the nil guards move from `req.Msg` onto `req` itself, refusing the same
empty submissions they refuse today.

The mounting seam keeps its shape one level down. Where
[provider.go](/pkg/modules/topology/impl/measured/provider.go) spreads the
generated pair into a `scionrpc.Mount` today, it builds a `*connect.Server`,
registers the service, and lets `connecthttp.Mount` spread the server over
a private mux; the tuple the provider returns carries the generated service
name's canonical pattern with that mux as its handler. The voting
application's `MountControlEndpoint` call and the WireGuard directory's
own-socket mux do the same, each in its own server. The endpoint mux's
precedence is untouched — the drafts' own registrations and the
`peeria.Authenticate` wrapper keep their places, the wrapper now wrapping
the mounted mux as it wrapped the bare handler.

### The clients

The four client sites — the measured directory's publish client, the
provider's link client, the WireGuard directory client, and the voting
submitter — wrap their `*http.Client` once: `connecthttp.NewTransport`
takes the client and the `"https://" + authority` base URL the sites build
today, and `connect.NewClient` wraps the transport into the generated
constructor. The per-authority caches and rebuild-on-route-move logic keep
reading the same authority strings. `connect.NewRequest` leaves every call
and `.Msg` every reply: the client call takes the message, the reply is
the message.

### The errors

The twenty-three `connect.NewError` sites across the four own services
become message constructors: `connect.NewError(code, errors.New("..."))`
drops the `errors.New`, and the sites that forward an error — the voting
service's parse wrap and its `DecideTRC` return — state their own message
and chain the cause with `.WithCause(err)`, keeping `errors.Is` and
`errors.As` whole for the server's own logs and tests while the wire
carries only the stated text. `connect.Errorf` serves the sites that
interpolate. The voting submitter's `CodeOf` check is unchanged in v2 and
keeps turning `CodeNotFound` and `CodeUnimplemented` into
`trust.ErrNoVotingApp`.

### The read bound

v2 refuses messages past 4 MiB with `CodeResourceExhausted`; the migration
tool's habit of pinning `WithReadMaxBytes(0)` to preserve v1's unbounded
reads is declined. The largest message the own services carry is the
voting submission's DER-encoded TRC, a kilobyte-scale object with its
certificates inside; everything else is strings and small integers. The
bound stands as shipped.

### The migration pass

The guide's sequence runs scoped to the four seams: the migration tool's
dry-run diff over the own packages is the checklist of rewrites, its
`-w` pass and the `buf generate` regen land them, a second pass binds the
call sites to the regenerated packages, and `go mod tidy` settles both
modules. The tool rewrites module-wide, so its diff is trimmed to the four
packages before anything binds — the control-plane packages it reaches are
reverted to v1, the one manual seam the guide leaves open by design. The
repo runs the same gate as any change: `go test -race -count=2`,
golangci-lint, goimports, `go fmt`, `go fix`, `go vet`.

## Compatibility

The wire is invariant in both directions: service paths, protocols served,
and message encodings are unchanged — v2 reorganizes the Go API, not the
protocols — so a rolled network mixes v1-built and v2-built nodes freely,
and the labs' scenarios observe nothing. Within one binary, the two connect
versions coexist on disjoint packages; no value crosses between them, and
the one exported signature that names a connect type,
[client.go](/pkg/core/controlplane/client.go)'s `NewClient`, stays v1 with
its callers. When scionproto/scion ships v2-generated control-plane code, a
follow-up proposal moves the drafts' services and drops the v1 requirement;
until then v1 remains maintained, and the split costs one extra module in
`go.mod`.

## Test plan

*   **Handler units:** the direct-call suites — the measured directory and
    link service, the WireGuard directory, plus the voting service — call
    methods with bare messages; the nil and empty guards refuse the same
    submissions with the same codes
    ([directory_test.go](/pkg/modules/topology/impl/measured/directory_test.go),
    [linkservice_test.go](/pkg/modules/topology/impl/measured/linkservice_test.go),
    [directory_test.go](/pkg/apps/wireguard/directory_test.go)).
*   **The client round trip:** the voting suite's in-memory transport test
    keeps its `RoundTripper` and its mounted-pattern assertion, the client
    now built over `connecthttp.NewTransport`; `CodeOf` still maps the
    unmounted application to `trust.ErrNoVotingApp`
    ([voting_test.go](/pkg/apps/voting/voting_test.go)).
*   **The read bound:** an oversized publish through the in-memory
    transport answers `CodeResourceExhausted`, pinning the adopted default
    where it enters.
*   **The labs:** the testnetwork suites rerun as written — same scenarios,
    same assertions, their generated clients riding the regen — and the
    full gate passes: `go test -race -count=2`.

## Implementation history

*   The move landed whole, the guide's rewrites made directly over the
    four seams: the four connect packages regenerated by the v2 plugin
    with [buf.gen.yaml](/buf.gen.yaml)'s version pins restated for it,
    the four services taking the request messages directly with their
    nil guards moved onto the requests themselves, and the twenty-three
    error sites restated — the forwarding ones chaining their causes
    with `WithCause`, the interpolating ones taking `Errorf`
    ([voting.go](/pkg/apps/voting/voting.go),
    [directoryservice.go](/pkg/apps/wireguard/directoryservice.go),
    [directory.go](/pkg/modules/topology/impl/measured/directory.go),
    [linkservice.go](/pkg/modules/topology/impl/measured/linkservice.go)).
*   The mounting seam kept its shape one level down — the provider's two
    services, the voting application's, and the WireGuard directory's

    spreads over a private mux, the tuples and mounts carrying the

    `connect.NewClient`, the per-authority caches and the submitter's
